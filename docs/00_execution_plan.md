## 2. 阶段与输出

### 阶段 A：只读环境与现有任务检查

先检查当前目录是否位于目标 AutoDL。目标尚未连接时，明确说明没有服务器结果，不能把 ChatGPT 容器的 GPU/CPU 当作目标机器。

读取 AGENTS，运行本仓库 `scripts/inspect_host.py`，补充必要的人工只读检查。记录现有任务及其资源使用的摘要、实际可用空间、是否存在可复用的 CUDA Toolkit、Conda 管理器、已有数据和预训练权重。盘点原始记录保留 .local，公开报告只给脱敏必要字段。

识别真正可用的 96GB GPU 和现有任务后，决定本轮 GPU 工作是可执行还是进入资源等待。CPU 数据准备和下载也遵守低负载预算。不得用“显存还有余量”推断可无影响同时训练。

输出：`reports/host_summary.md`、`reports/reuse_inventory.json`、更新 `reports/latest_status.json`。

### 阶段 B：创建专属 Conda 与进程环境

按照 docs/01，在项目数据盘目录新建 .local/conda/dn-splatter-bw。先复用可只读使用的系统工具链和下载缓存内容，再安装到新前缀。优先用已存在的 Conda 管理器，不重装或修改 base。

GitHub 访问优先本项目子 shell 内 AutoDL 官方学术加速。固定官方源码 SHA。安装候选组合 Python3.10/PyTorch2.7.1-cu128/torchvision0.22.1/Nerfstudio1.1.3/gsplat1.0.0，必要时仅针对真实编译错误最小适配。

输出：实际 `pip freeze`、Conda 显式清单的脱敏版本、torch/CUDA/nvcc/driver/gsplat 信息、源码与补丁 SHA。不能把建议版本写为已安装版本。

### 阶段 C：必要的实际兼容检查与场景准备

需要的检查只有直接决定正式实验的事项：

- 目标 GPU 被正确识别，两个 gsplat 后端可编译和加载；RGB/depth/normal 路径的实际计算及梯度有限。
- vr_room 输入路径、相机参数、long/short 两轨迹和 train/test 划分正确；RGB/深度/法线一一对应。
- Omnidata 权重可用，法线方向与历史 parser 约定一致；初始化点云来自允许的训练数据，实际点数被记录。
- 训练损失项按固定历史源码生效；不在这一阶段擅自替换成论文公式修订版。

用小批真实数据完成必要的兼容检查后，立即进入完整 30k。不要把短运行当正式结果，也不继续增加无关诊断。

### 阶段 D：累计 30,000 次训练更新

执行 docs/02 的版本匹配命令。设置每 5,000 步保存，并保存模型、优化器和 scheduler 状态；保持原实验学习率调度、法线和深度配置。

初次运行 max_num_iterations=30000；恢复时按 checkpoint 的零基 step 计算剩余更新数。目标最后 checkpoint step=29999。保存本轮及前序运行计数，防止实际做了 30k 之外的额外更新而仍标称 30k。

后台训练不设置完成时限。只监控本项目进程；发现本项目导致可见资源冲突，应在可恢复点让本项目退出并排队，不能处理其他项目进程。

输出：完整 command、config、seed、各阶段时长、峰值 GPU/RAM、checkpoint、训练曲线和高斯计数。

### 阶段 E：评估、渲染、Poisson 和几何指标

按 docs/02 分别得到官方原始 RGB/深度指标、实际渲染、Faro 原始与审计指标、Poisson 网格和可见性裁剪后的网格指标。

注意：500 万是网格采样目标，不是训练初始化数量；训练初始化目标约 100 万，实际值另记。Poisson depth=9，F-score 阈值 0.05m。显式限制本项目网格处理线程。不能以换 TSDF、降采样、换场景代替失败的论文协议。

渲染与网格至少人工或图像工具检查代表视角：墙/桌面、边缘、遮挡、薄结构与漂浮物。记录实际缺陷而非只放一个最好看的视角。

### 阶段 F：保存结果、推送、汇报

先向用户仓库推送小文件：环境与补丁、config、实际命令、指标、代表图、结论、完整产物清单。大 checkpoint/网格/数组保留在本项目 .local 并登记路径、字节数、sha256和上传状态；如有既定大文件目的地可后台继续上传。未上传不能写已备份。

最后报告是否完成完整流程、与论文目标的实际差距、原始和审计指标区别、还需要修复什么，以及是否影响过其他任务。不得把计划提交和本地脚本语法检查当成服务器运行通过。

## 3. 单轮持续推进与真实阻塞

“一次性完成”指一个持续工作流可以从检查一路推进到结果，不代表保证一个固定小时数内结束。

- 编译、依赖、路径、普通数据错误：在本项目范围内自行排查和最小修复，记录后继续。
- 原 GPU 任务仍活跃：维持可恢复的持久排队；能够做的低负载 CPU 工作继续。已有任务释放资源后自动重新评估，不能因一次检查繁忙就放弃整轮。
- 磁盘不足：不删除其他项目；先确认本项目重复下载和可复用数据，仍不够则报告明确容量与阻塞点。
- 数据或权重获取失败：先 AutoDL 官方加速（适用域）和原始官方来源，记录 URL/状态；不以未经验证的替代权重继续冒充原实验。
- 服务器、GitHub 或所需数据权限确实不可得：提交可保存的诊断与准确的下一条操作，明确缺少什么。
