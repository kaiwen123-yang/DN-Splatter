# 本地 `H:\capture.bag` 只读审计与回传

## 1. 本轮任务与完成边界

用户已明确给出本地输入 `H:\capture.bag`，估计约 6 GB。**本轮先由能够访问该盘的本地 Codex 检查数据，再把小报告和少量样本回传，供 ChatGPT 判断 DN-Splatter 接入路线。** 这份文档是执行手册，不表示该文件已经被读取，也不预设它是标准 ROS1 bag、含 RGB-D 或含相机轨迹。

先读仓库 `AGENTS.md`、本文件、[自有数据接入说明](06_custom_data.md) 和 `configs/capture_bag_audit.json`。当前用户要求覆盖先前“自有数据通过检查后自动开训”的安排：本轮不启动自有场景训练、全量转换、完整 SLAM/COLMAP、法线模型推理或新一轮 AutoDL 实验；不终止、暂停、改动已经运行的 AutoDL 任务。完成回传后等 ChatGPT 根据实际结果提出下一步，这是用户指定的工作顺序。

本轮应回答六个问题：

1. 文件实际是什么格式，能完整读取多少数据，有哪些数据流？
2. RGB、深度、内参、时间戳、外参和相机位姿分别有什么证据，缺什么？
3. RGB 与深度是否能可靠配对，是否在同一像素坐标系下？
4. 场景和相机运动是否提供了可用的多视角观测，动态、模糊、缺测和漂移有哪些风险？
5. 哪个时间段、哪组话题最适合做第一个自有场景，下一步需补什么处理？
6. 是否具备进入数据转换验证的条件；不能把“文件可读”或“样本好看”写成“可以直接训练”。

## 2. 本机检查与隔离

只检查明确输入路径、当前项目目录以及实际执行所需的解释器/工具位置。不要递归扫描 H 盘、用户目录或其他项目来猜数据位置。

| 实际执行环境 | 输入路径和处理 |
| --- | --- |
| 用户 Windows 本机 | 用原生 Python 读取 `Path(r"H:\capture.bag")`；先核实路径存在、为普通文件、可读及剩余空间 |
| 已有 WSL | 先确认该 WSL 已存在，并确认转换后的路径确实可读；只有实际观察到后才使用 `/mnt/h/capture.bag`，不能假设 H 盘已挂载 |
| 仅 AutoDL/远程 Linux | 不能把远程服务器上的不存在路径当作本地文件；保存 `blocked_path_access` 报告和可继续执行的本地入口，不要求上传整个 bag |

记录本机 OS、Python 路径/版本、实际 CPU/RAM、项目输出盘空闲空间和依赖版本。AutoDL 的 25 核、120 GB RAM、96 GB 显存不是本机配置。本轮主要是 CPU 与顺序 I/O，不需要复刻 Blackwell/CUDA 训练环境，也不需要 GPU 压测。

优先复用合适的现有 Python，在项目 `.local/` 下创建专用 venv 或独立 Conda prefix，例如 `.local/venv/bag-audit`；使用其解释器执行 `python -m pip`。不向 base、系统 Python 或其他项目安装、升级和卸载包，不修改全局 Git/pip/Conda 配置。依赖选择应以现场 Python 兼容性为准，记录实际锁定版本和最少必要依赖，通常为 `rosbags`、图像解码所需库以及 `numpy`。

[`rosbags` 官方文档](https://ternaris.gitlab.io/rosbags/)明确说明它可以独立于 ROS 软件栈读取 rosbag1/rosbag2。因此先尝试轻量离线读取，不强制安装 ROS、Docker、WSL，不启动 ROS master、不播放到 ROS 网络、不连接真实机器人。确有已识别厂商格式时，可使用兼容该记录版本的官方只读 reader/SDK；先检查现有工具，再在本项目隔离环境中补最少依赖。

GitHub 使用本机已有安全连接和凭据。本机不要套用 AutoDL 代理；仅当实际在 AutoDL 执行 GitHub 操作时，按 `AGENTS.md` 优先使用官方学术加速。不输出令牌、完整环境变量、代理信息或其他项目的进程参数。

## 3. 原文件身份、格式和完整性

所有读取均只读打开。原文件不复制、不改名、不重索引、不重写、不更改权限；不得对原文件执行 `rosbag reindex`、转换器或修复工具。约 6 GB 不是本轮必须复制一份的理由。

按顺序记录：

1. 开始时的精确字节数、修改时间和文件类型，少量文件头 magic；不要只根据 `.bag` 后缀判断格式。
2. 顺序流式计算整个文件的 SHA-256，得到精确 `bag_sha256`，使用固定大小读取块，不能整文件读入 RAM。
3. 识别实际容器、版本、压缩方式、连接信息和内嵌消息定义。标准 ROS1、ROS2 存储、厂商 SDK 的历史记录格式分别处理。ROS2 若需要同一记录的 metadata/分片，先根据输入自身证据指出缺失项，不能把单个文件当成完整多分片记录，也不能搜索整盘补齐。
4. 遍历实际可访问消息，记录声明消息数、读取消息数、反序列化成功数、未知类型、异常位置、结束方式及各阶段覆盖范围。SDK 回放应选择离线、非实时、非循环方式，避免因回放速度丢帧；记录实际 API 和版本。
5. 结束后再次检查文件大小和修改时间。若变化，标记 `source_changed_during_audit`，不能把计数和哈希包装成同一静态版本的完整审计。没有变化时也只声明“审计过程未发现大小/mtime 变化”，不夸大成外部程序绝对未修改。

`rosbags` 不支持某个容器版本、缺消息定义、编码器缺失或 SDK 不兼容，都不等于文件损坏。区分 `unsupported_format`、`missing_message_definition`、`unsupported_image_codec`、`truncated_or_corrupt` 和其他实际异常；无法判定原因时写 `unknown`。即使部分流不可解码，也继续盘点能读取的流并保存部分结果。

若确需修复，只提出原文件之外的项目副本方案、所需空间和实际错误证据。本轮不自动复制大文件或尝试原地修复。遇到路径不可达、磁盘容量不足等真实阻塞时，报告具体缺项和已完成证据，不伪造成功。

## 4. 话题和消息类型盘点

以 connection/type 定义为依据盘点所有话题，不能只匹配 `color`、`depth`、`pose` 等名字。对同一话题的多连接、多消息类型或定义变化保留区分。

每个话题至少给出：

- 原始话题名、连接 ID、消息类型、schema/MD5 等可用标识及定义来源；完整自定义消息定义可保留本地，公开报告给必要字段与哈希。
- 消息声明数、实际扫描数、成功解码数、错误数、起止记录时间、持续时长、平均及中位间隔对应频率。
- 累计序列化 payload 字节、占比。明确它不是压缩后 bag 文件内的精确磁盘占用，不能将两者混称。
- 是否有 header、frame_id、序列号，以及尺寸/编码变化的次数和时间段。
- 类型分类：RGB/灰度/红外、深度/视差、CameraInfo、TF/static TF、Odometry/Pose/Path、IMU、点云、关节、GNSS 或厂商元数据。没有的类别明确写 `not_present`。

先完整盘点，再选推荐 RGB、depth、CameraInfo 和 pose/TF 来源。保留其他候选及不选原因；原始 RGB 和其压缩副本不能算成两台独立相机。多个相机/深度源、多个 pose 估计器分别报告，不能无说明拼接为一个流。

[`AnyReader` 官方接口](https://ternaris.gitlab.io/rosbags/topics/highlevel.html)可读取 ROS1 或 ROS2，并自动注册记录中保存的消息定义；不要在同一个 reader 上并发或交错运行独立消息迭代器。需额外类型定义时，按[官方自定义类型示例](https://ternaris.gitlab.io/rosbags/examples/register_types.html)优先使用 bag 内定义，再使用来源明确的匹配 `.msg`/`.idl`。不能猜自定义二进制布局，不随意选一个 ROS 发行版的 typestore 来掩盖类型不匹配。

可以顺序扫描消息，在本地保存轻量时间数组/计数；仅把少量已复制出来的样本交给图像处理 worker。不要把全 bag 消息、所有图像或所有点云长期堆进内存，也不要用大量并发 reader 重复读约 6 GB 文件。

## 5. 时间完整性与跨流同步

### 5.1 时钟定义与扫描范围

至少对所有可读取记录统计 record timestamp；对推荐图像流、相关 CameraInfo、TF、pose/odom、IMU 完整扫描可获得的 header/device timestamp。其他流明确哪些仅做结构盘点、哪些也完成时间分析。图像像素只抽样，不代表时间戳也只抽样。

绝对时间在计算中用整数纳秒；JSON 中用十进制字符串保存，避免 JavaScript 浮点丢精度。求差后再转换为毫秒/秒用于统计。记录原时间字段、单位、时钟域判断证据；设备启动时间、ROS 仿真时钟和 Unix 时间不得直接混配。

分别给出 record/header 的零值、重复、回退、间隔异常、最长空洞、间隔分位数及 record-minus-header 偏差/漂移/跳变。没有时钟关系证据时，record-minus-header 不能直接解释为传输延迟。TFMessage 没有统一外层 header 时，逐条检查内部 transform 自身的 header。按时间段识别设备重启和时钟复位，不能跨复位段强行关联。Image 中全零采集时间需要特殊处理；静态 TF 或一次发布的标定信息出现零戳可能合法，不能统一判坏。

特别注意：`AnyReader.messages()` 会按记录时间排序。**排序后递增不证明原始磁盘写入顺序没有倒序。** 报告必须说明遍历顺序与可证明范围；无法读取原始存储顺序时将该项标为未知。相对于记录时间顺序，header 回退、重复和 record-header 跳变仍可报告。

### 5.2 RGB—depth 配对

只有证据支持同一时钟域时才优先使用采集/header 时间；否则可另外做 record-time 诊断，但不能据此保证采集同步。每种候选配对记录：源话题、时钟字段、有效时段、配对算法、容差、一对一约束及原始候选数量。

推荐同时报告最近邻诊断和可用于导出的唯一配对结果：有符号差 `t_depth - t_rgb` 与绝对差的 p50/p95/p99/max，未匹配比例、深度帧复用比例、5/10/20/33 ms 等容差下覆盖率。容差只是诊断，不是所有设备通用的合格线。相机运动速度、曝光和帧率都会影响可接受误差。

可以拟合时钟偏移/漂移作为诊断，但不能静默修改原时间戳并把校正结果当成原始同步。原始结果与假设校正结果分别保存，记录拟合样本、误差和不适用区间。用 CameraInfo 的时间有效区间关联标定，不能因为静态标定只出现一次就判定后续全缺失。

### 5.3 位姿时间覆盖

对每个推荐 RGB 帧判断是否有可用 camera pose 或可在该时刻组合出的 TF。报告插值两端间隔、覆盖率、缺失区间和跨跳变情况；不能以“最近一条 TF”无限期代替动态位姿。默认不对超出覆盖范围的动态位姿外推，不跨轨迹重置插值。任何插值规则和最大允许间隔都必须显式记录。

## 6. 图像、深度与代表样本

### 6.1 解码保持原始语义

对未压缩 Image 记录 `height/width/encoding/is_bigendian/step`、数据长度、通道含义和实际 dtype。`step` 是含行填充的完整行字节数，不能一律用 `height × width` 直接 reshape；检查边界和字节序。依据为 [ROS Image 消息定义](https://github.com/ros/common_msgs/blob/noetic-devel/sensor_msgs/msg/Image.msg)。

对 CompressedImage 保留 `format`、原编码、实际 codec 与解码器版本。可使用 [`rosbags-image` 官方 API](https://ternaris.gitlab.io/rosbags-image/api/rosbags.image.html)处理已支持的标准图像，但必须验证安装版本实际支持的编码。

**`compressedDepth` 不能当作普通 JPEG/PNG 处理。** 其 payload 可能包含配置头；32 位浮点深度可能经过逆深度量化，且存在 PNG/RVL 与历史格式差异。按匹配的[官方 transport 实现](https://github.com/ros-perception/image_transport_plugins/blob/rolling/compressed_depth_image_transport/src/codec.cpp)识别和还原；不能随意截掉猜测长度的头、只 `imdecode` 后就称原始深度。缺少正确 decoder 时记录明确阻塞，继续其他流的审计。

灰度/红外、Bayer、YUV、RGB/BGR 顺序分别说明。深度不能转成 8 位彩色图再做数值统计；彩色热力图仅供预览。视差也不能直接当深度，转换需要有证据的相机参数和单位。

### 6.2 深度单位与有效性

优先从实际驱动/SDK 元数据、depth scale、记录的明确参数或匹配的消息契约确定单位，并给出处。[REP 118](https://reps.openrobotics.org/rep-0118/)规定其标准浮点深度为沿光轴 Z 的米，OpenNI 原始 uint16 表示毫米；这项约定不证明任意厂商/自定义 `16UC1` 或 `32FC1` 都遵守它。

没有证据时必须写 `depth_unit: unknown`、`scale_to_meters: null`，可以给出候选假设及量级合理性，不能自动乘 `0.001`。CameraInfo 本身不提供深度比例；数值看起来像几米也只能做合理性检查。区分 optical-axis Z、沿视线距离、逆深度和视差。

对实际解码样本统计原始 dtype、有限值比例、零值、NaN、正负 Inf、其他已知无效值/饱和值、有效像素比例、有效值 p1/p50/p99/min/max、空洞与边缘缺测。不要把 NaN/Inf 先替换为零后丢失原始分类。单位未知时统计原数值；只有单位已确认时再给米制距离。

### 6.3 覆盖全时段的取样

默认按**全局时间均匀分布**选择约 24 个代表时刻，覆盖开始、中间和结束；用源索引和实际时间查找最近的有效候选，不只取文件前几秒，也不只选好看的帧。候选帧不足时全部使用并如实说明。相机/编码切换、长空洞、严重模糊、时钟复位等事件可补充少量异常样本，单独标明选择原因。

对这些样本计算图像清晰度、曝光/饱和、重复画面、RGB/depth 有效覆盖与动态内容观察。阈值需给定义，清晰度分数仅作本数据内相对比较；24 张像素样本的结论不能写成对所有帧做过像素检查。若需更密集的像素统计，可以流式增加低成本抽样，但报告准确的抽样数、比例和规则，不全量导出。

预览建议为全时段 RGB 联系表、相同时刻深度热力图、时间覆盖/同步误差图和必要的配准检查图。深度热力图标明单位、颜色范围和无效像素颜色；多个画面比较时尽量共享同一数值范围。

### 6.4 RGB—depth 注册与少量可复核样本

同分辨率、相近时间戳或把深度 resize 到 RGB 尺寸，都不证明深度已注册到 RGB。检查实际话题定义、frame_id、对应内参、畸变、RGB-depth 外参和驱动注册记录。具备真实参数时，对少量帧做深度反投影及 RGB 重投影，检查可见边缘、遮挡、重叠范围和误差；缺参数时将注册状态写为未知，不制造对齐图。

回传 `samples/` 默认 3 组、必要时最多 5 组代表样本，每组使用同一索引标识 RGB、匹配深度和元数据。RGB 使用保真图像；深度使用保留原 dtype/数值的无损 NPZ，或适用于 uint16 的 16 位 PNG，读回后检查数值。保留无效值语义；浮点深度不得量化为整数/8 位图来省空间。

每组写明源话题与连接、帧序号、record/header 时间、配对时钟与时差、原图尺寸/编码、raw dtype、深度单位证据、CameraInfo 关联和 pose 可用状态。原生 RGB 与原生深度本来不对齐时照实保留，各自内参不能混用。若预算逼迫使用 ROI，必须保留像素原值并记录原尺寸、裁剪矩形和内参坐标映射；先减少到 3 组再考虑 ROI，不隐瞒缩放/裁剪。样本用来复核数值和几何，不要求整段数据上传。

## 7. 标定、坐标系、TF 与轨迹

### 7.1 标定盘点

逐相机记录 CameraInfo 的 frame_id、`K/D/R/P`、distortion model、标定尺寸、binning、ROI、出现时段、不同参数版本及参数哈希。检查矩阵有限性、焦距、主点、图像尺寸与标定匹配情况。按 [CameraInfo 定义](https://github.com/ros/common_msgs/blob/noetic-devel/sensor_msgs/msg/CameraInfo.msg)，`K[0] == 0` 可表示未标定；raw 图像和 rectified 图像的相机模型需分别对应 `K` 与 `P`，不能把它们不加区分地复制。

不同颜色/深度/红外光学帧各自建档。只存在某个相机的标定，不代表所有图像都具有对应内参。镜头变焦、裁剪、降采样及 SDK 默认处理需如实记录；公开报告只列重建相关参数，不转储全套 ROS 参数。

### 7.2 TF 和多种 pose 来源

绘制或列出 TF 图的 parent→child、静态/动态属性、数量、时间范围和覆盖。检查循环、同一 child 的冲突 parent、同名冲突、非有限值、四元数范数异常、静态外参变化和动态跳变。公开图使用必要 frame 名；发现包含敏感定位信息的名字时建立可追踪的本地别名映射。

区分“TF 图连接存在”和“图像采集时刻存在正确动态变换”。一组相机安装静态 TF 不提供相机在场景中的移动轨迹；只有 IMU/关节数据也不自动得到可信 6DoF camera pose。里程计、机器人底座、末端执行器或 IMU pose 必须经过已知外参/手眼标定和时间关联才能变成相机光心位姿。GNSS 坐标或一条 path 消息不等于已满足这些条件。

每个 pose 候选注明来源、坐标系、单位、world/local 语义、c2w/w2c 方向、四元数分量顺序、可用质量字段、轨迹重置/回环修正与漂移迹象。无 covariance 或 covariance 全零不能当成零误差；轨迹完整也不能直接宣称准确。保留不同估计器结果，不默认融合。

### 7.3 相机轨迹与公开相对坐标

仅在变换和时间关系成立时，计算选定 RGB optical frame 的轨迹及每帧覆盖率。报告轨迹时长、路径长度、净位移、范围、旋转变化、重复驻留、突变和可疑漂移；单位未确定时不能标成米。保留“原始数据中的实际运动证据”和“图像推测”两种证据的区别。

局部光流、匹配点变化和画面差异可以帮助诊断，但可能由纯旋转、动态物体、曝光变化或移动显示内容产生；不能据此断言相机平移或已具备三维可观测性。评估静态背景比例、多视角重叠、明显动态物体、长时间停驻以及可疑纯旋转。没有可信 pose 时给出下一步估计位姿的候选路线，不在审计中直接启动完整重建。

原始绝对轨迹只放 `.local/` 私有输出，公开样本和轨迹图使用首个有效相机为参考的相对坐标。若原始矩阵定义为 `T_W_C(i)`，可使用 `T_C0_C(i) = inverse(T_W_C(0)) @ T_W_C(i)`。记录变换定义、单位和相对参考帧，但公开文件不能附上会恢复绝对位置的原点变换、原始 GPS、UTM/ECEF 平移或定位地址。公开相对轨迹也要注明只完成坐标归零，并未完成精度验证。

## 8. 回传接口与体积

本地中间结果放项目 `.local/bag-audit/<run-id>/`，包括完整时间数组、必要原始坐标、详细日志与更多样本。公开结果统一放 `reports/capture-bag-audit/<run-id>/`，`run-id` 使用 UTC 时间和 bag SHA-256 短前缀等不会覆盖旧记录的标识。每次审计都必须能关联精确完整 `bag_sha256`、脚本版本和实际源文件身份。

以下名称与 `configs/capture_bag_audit.json` 对齐。不存在的数据也要输出带状态/原因的有效 JSON，不能用空白文件冒充检查完成。

| 文件/目录 | 必须承载的内容 |
| --- | --- |
| `overview.md` | 中文结论、数据概况、关键图、证据与未知项、适配路线、首段候选、下一步建议和实际阻塞 |
| `summary.json` | bag 哈希/格式/字节、审计状态、扫描范围、selected topics、association clock、各接入条件的 `confirmed/missing/unknown/not_applicable/failed` 与证据路径；字段和枚举遵循配置中的接口 |
| `topic_inventory.json` | 所有话题/连接/类型、实际计数、数据量、时间范围和 schema 来源 |
| `timing.json` | 时钟语义、逐流完整性统计、复位/空洞、扫描覆盖与排序限制 |
| `sync.json` | 推荐及候选配对、容差覆盖、signed/absolute 时差、唯一配对/复用情况和校正假设 |
| `calibration.json` | 必要 CameraInfo/SDK 标定、版本、RGB-depth 外参及单位证据、缺项 |
| `frame_graph.json` | 必要坐标链、静动态属性、时间覆盖、冲突及断链 |
| `trajectory.json` | 各 pose 来源判断、相机 pose 覆盖、相对轨迹摘要和问题；不公开绝对定位原点 |
| `image_quality.json` | RGB 抽样方案、尺寸/编码变化、清晰度/曝光/重复/动态观察及局限 |
| `depth_quality.json` | 原始数值分布、无效值、单位/尺度证据、注册判断、抽样数量及局限 |
| `samples_metadata.json` | 预览和数值样本的来源索引、精确时间字符串、配对时差、原 dtype、像素映射、标定与相对 pose 状态 |

大文件原包、全量帧、全量点云、完整参数转储、原始 GPS/绝对坐标、凭据和环境都不得进入 Git、Git LFS 或任何云上传。本轮不为数据开新存储账号、不发整包压缩包。每个文件要有可解释的用途；不靠本地文件链接让公开报告引用读者无法访问的关键证据。

## 9. 接入结论如何写

先给事实，再给建议。至少逐项评估 RGB 可读、深度可用及单位、内参匹配、时间同步、RGB-depth 注册、每帧相机位姿、静态多视角覆盖；每项附证据、覆盖范围和未解决问题。

| 实际证据 | 本轮允许给出的下一步结论 |
| --- | --- |
| RGB-D、标定、单位、注册、同步、相机位姿均有证据，场景具备静态多视角 | 可进入小规模转换与几何验证；不能跳过 dataparser 坐标/尺度核验，也不能在本轮自动训练 |
| RGB-D 与标定可用，但缺可靠相机轨迹 | 先规划 RGB-D/视觉惯性 SLAM 或其他有依据的位姿求解，并验证尺度、漂移与相机外参 |
| 只有合适 RGB 多视角、没有可用传感器深度 | 可考虑 RGB/SfM 与单目先验路线；明确这会改变输入条件，不等同于已复现的传感器深度实验 |
| RGB/depth 未注册或单位未知 | 先补对应标定、驱动元数据和小样本注册验证，不能直接接 sensor-depth 监督 |
| 固定相机、纯旋转、严重动态、覆盖不足或严重模糊 | 说明具体不足，提出补采/换段/动态建模需求，不仅凭总帧数判断可训练 |
| 格式、类型或解码尚未解决 | 交付已确认元数据和精确缺失项；当前适用性为未知，不把工具失败称作数据不合格 |

可提出一个推荐起止区间、相机/话题组合、预计关键帧策略以及预估导出体积，但必须说明估计依据和不确定性。本轮不做全量导出、不生成虚构 transforms、不将 VR Room checkpoint 当成新场景通用推理模型。后续转换细节参见 [docs/06_custom_data.md](06_custom_data.md)。

## 10. 完成与回传

保存可复现的审计脚本、最少依赖版本和实际命令，脚本放仓库受跟踪的 `scripts/` 中，不能只留在 `.local/`。命令参数显式包括输入路径、输出目录和配置；发布报告不写凭据或无关主机信息。验证报告 JSON 可解析、相对路径有效、数值样本能按原 dtype 读回，计数和体积与 manifest 一致即可，不为本轮堆叠无关测试。

完成后检查源文件状态、阶段状态和实际覆盖。公开文件使用明确路径逐个暂存，检查 staged diff、敏感内容及体积，再按已有用户授权回传本仓库；不 `git add .`、不 force push、不给上游仓库推送。网络/权限受阻时保留本地产物并给实际错误及重试入口，不声称已推送。
